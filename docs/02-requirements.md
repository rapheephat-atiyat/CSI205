# 02: ข้อกำหนดการทำงานของ TUATUA

อ่าน [ภาพรวมและสถานะเอกสาร](README.md) ก่อน รายการ REQ มาจาก PDF หน้า 1-3 และคำตอบของผู้ใช้ ส่วนรายละเอียด DESIGN และคำถาม OPEN ยังไม่ใช่ข้อยุติ

## 1. เป้าหมายและขอบเขต

TUATUA เป็นเว็บจัดการงานเลี้ยงรุ่นหลายงาน ตั้งแต่ลงทะเบียน ซื้อบัตรและเสื้อ ออก QR เข้า-ออกงาน ใช้ Token ซื้อสินค้า ไปจนถึงคืน Token และตรวจยอดหลังจบงาน

**REQ-001** บัญชีหนึ่งเชื่อมหลายงานและหลายร้านได้ งานและร้านต้องเป็นตารางแยก ใช้ความสัมพันธ์ `user_events` และ `store_members` ที่มีอยู่ ห้ามย้ายข้อมูล Event/Store ทั้งก้อนลง JSON หรือ array ใน `users`

**REQ-002** ผู้ซื้อ ผู้เข้าร่วม และตั๋วเป็นคนละสิ่ง บัญชีหนึ่งซื้อให้เพื่อนหลายคนได้ ห้ามใช้ `buyerUserId` แทนผู้ถือบัตรทุกใบ

**REQ-003** ข้อมูลและสิทธิ์ต้องแยกตามงาน ร้านเห็นเฉพาะร้านที่ตนดูแล Staff ของงาน A ไม่มีสิทธิ์งาน B โดยอัตโนมัติ

**REQ-004** เวอร์ชันต้นทางใช้การชำระเงินจำลอง ไม่มี Payment Gateway และบัตรเครดิต การรับโอน/ตรวจสลิปจริงยังเป็น OPEN D10 ห้ามเชื่อมบริการเงินจริงเอง

## 2. ผู้ใช้และขอบเขตสิทธิ์

| ผู้ใช้ | การทำงานตาม REQ | ขอบเขต |
| --- | --- | --- |
| Guest | DESIGN: ดูรายละเอียดงานที่เปิดเผยและ catalog | ไม่มีข้อมูลบัญชี/ผู้เข้าร่วม/ยอดเงิน |
| User | ลงทะเบียน โปรไฟล์ ซื้อบัตร/เสื้อ ดูคำสั่งซื้อ ตั๋ว QR Token และคำขอคืนของตน | เฉพาะทรัพยากรที่เป็นเจ้าของหรือได้รับสิทธิ์ |
| Super Admin | ตั้งค่างาน ราคา เรท Token สิทธิ์ผู้ดูแล ร้าน การคืน Token และรายงาน | ระดับระบบ ต้องมีขั้นตอน bootstrap ที่ควบคุมได้ |
| Event Admin | DESIGN: ผู้ดูแลงานตาม `user_event_roles.admin` และสิทธิ์รายคน | เฉพาะ event ที่ได้รับมอบหมาย |
| Staff | สแกนเข้า-ออก ค้นหาผู้เข้าร่วม เติม Token ตามสิทธิ์ | เฉพาะ event ที่ได้รับมอบหมาย |
| Vendor | จัดการสินค้า/ราคาของร้าน สแกนรับชำระ ดูยอดขายร้านตน | ต้องผูก `store_members` ของร้านนั้นด้วย |

REQ ระบุว่าร้านค้าเติมหรือคืน Token ไม่ได้ การมี `vendor` จึงไม่ให้สิทธิ์ `token.topup` หรือ `token.refund.approve` โดยตัวมันเอง ถ้าบัญชีเดียวทำหลายหน้าที่ ต้องตรวจบริบทและสิทธิ์ Staff/Admin แยกจากบริบทร้าน

`user_roles` ในโค้ดอนุญาตทั้งห้าค่า แต่ความหมายของ global `admin/staff/vendor` ยังไม่มี implementation ให้ดู [D11](#8-ทะเบียนเรื่องที่ยังต้องยืนยัน) ห้ามตีความว่าทุกบทบาทระดับบัญชีทำงานข้าม event ได้

## 3. ขั้นตอนการใช้งานและเกณฑ์ตรวจรับ

### REQ-010: บัญชีและโปรไฟล์

1. สมัคร/เข้าสู่ระบบผ่านกลไก auth ที่ตกลงใน D00
2. ลงทะเบียนข้อมูลชื่อ รุ่นเป็นปี พ.ศ. คณะ ข้อมูลติดต่อ และอีเมลก่อนซื้อ
3. ดูและแก้โปรไฟล์ตนเองได้ โดยไม่แก้ role/status/permission จากฟอร์มโปรไฟล์
4. บันทึกความยินยอมที่เกี่ยวข้องพร้อมเวอร์ชันและเวลา ตามขอบเขตที่ตกลงใน D13

DESIGN: โปรไฟล์ที่ยังไม่ครบอ่านงานได้ แต่สร้างคำสั่งซื้อไม่ได้ (`PROFILE_INCOMPLETE`) ต้องเก็บปีรุ่นที่ผู้ใช้ระบุ ไม่บวก/ลบ 543 กับทุก field ที่ชื่อ year โดยเดา

ตรวจรับ: ผู้ใช้ A แก้โปรไฟล์ B ไม่ได้, บัญชี suspended ทำ protected operation ไม่ได้, signup ไม่รับ role สูงจาก request หรือ user metadata

### REQ-020: งานและ catalog

1. ผู้มีสิทธิ์สร้างงานและกำหนดรายละเอียด วันเวลา สถานที่ ช่วงขายบัตร และเรท Token
2. กำหนดประเภทบัตร ราคา Token ที่แถม จำนวนซื้อต่ำสุด/สูงสุด และจำนวนขายได้
3. กำหนดเสื้อ ขนาด ราคา และจำนวนที่มี
4. แก้ราคาภายหลังได้ แต่ต้องไม่เปลี่ยนยอดหรือรายละเอียด snapshot ของรายการเดิม

มีแล้วเฉพาะข้อมูล Event พื้นฐาน ยังไม่มีช่วงขาย เรท Token บัตร เสื้อ หรือ inventory

DESIGN: งานเริ่ม `draft`; เปลี่ยนเป็น `published` เมื่อข้อมูลที่จำเป็นครบ; `published -> completed` หลังหมดเวลา หรือ `published -> cancelled` ผ่านผู้มีสิทธิ์ งานปลายทางเป็น read-only สำหรับคำสั่งซื้อ/ขาย/เติมใหม่ ส่วนคืน Token ต้องเป็นไปตาม policy ที่ตกลง และทุก transition ต้องมี audit ห้าม auto ยกเลิก/คืนเงินจากการเปลี่ยนสถานะอย่างเดียว

ตรวจรับ: เวลาจบมากกว่าเวลาเริ่ม, slug งานไม่ซ้ำ, ไม่มี draft หลุดใน public list, สองคำสั่งซื้อแย่งจำนวนสุดท้ายต้องไม่ขายเกิน

### REQ-030: คำสั่งซื้อและการชำระเงิน

1. User เลือกบัตรหลายใบ พร้อมข้อมูลผู้เข้าร่วมแยกแต่ละใบ และซื้อเสื้อได้
2. Server ตรวจงาน/ช่วงขาย/จำนวน/ราคา/โปรไฟล์ แล้วคำนวณยอดจาก catalog ของ server
3. สร้างคำสั่งซื้อพร้อม snapshot ราคา ประเภทสินค้า Token ที่แถม และข้อมูลที่ใช้คำนวณ
4. ชำระจำลองผ่าน action ของ server แยกจากการสร้าง order
5. เมื่อสำเร็จ ออกบัตรหนึ่งใบต่อผู้เข้าร่วมที่ซื้อ และเครดิต Token ตาม policy เจ้าของกระเป๋าที่ตกลง
6. ผู้ซื้อดูคำสั่งซื้อและสถานะได้

DESIGN: order `pending_payment -> paid | expired`; payment `pending -> succeeded | failed`; การจ่ายสำเร็จซ้ำต้องคืนผลรายการเดิม ไม่ออกบัตรหรือเครดิตอีก การแก้รายการหลัง paid ต้องห้ามผ่าน PATCH ทั่วไป

เรื่องอายุ order/การกัน stock ยังต้องกำหนดใน D12 ให้ชัด การหมดอายุ order ที่ยังไม่จ่ายไม่ใช่การยกเลิกตั๋วที่ออกแล้ว

ตรวจรับ: ราคา/ยอดรวม/status ที่ client ส่งมาไม่มีอำนาจ, payment ของ order A ใช้กับ B ไม่ได้, เปลี่ยนราคาภายหลังไม่กระทบ order เก่า, failure ระหว่างออกบัตรต้องไม่เหลือ paid ที่ออกตั๋ว/เครดิตบางส่วนโดยไม่มี recovery ที่ทดสอบแล้ว

### REQ-040: ผู้เข้าร่วม ตั๋ว และ QR

1. ออกตั๋วหลังชำระสำเร็จเท่านั้น
2. เปิดตั๋วของตนและ QR เฉพาะผู้เข้าร่วมได้ตามรูปแบบ ownership ที่ตกลงใน D01
3. QR เปลี่ยนทุก 30 วินาที ตรวจความสดโดย server
4. ตั๋วยกเลิกหรือโอนไม่ได้ใน scope ต้นทาง ห้ามสร้าง transfer/cancel endpoint ของตั๋วเอง
5. การเปลี่ยน QR กับการกันใช้ซ้ำเป็นคนละกลไก ต้องมีทั้งสองอย่าง

DESIGN: QR เป็น token ที่ตรวจลายเซ็น/nonce/เวลาหมดอายุได้ ไม่มีชื่อ อีเมล ยอดเงิน หรือรหัสฐานข้อมูลล้วน ๆ ให้แก้เองได้ และห้ามใส่ลง log/URL query การใช้ภาพ QR เก่าไม่ได้ทำให้เกิดรายการใหม่อัตโนมัติ

ตรวจรับ: ผู้ใช้ A ขอ QR ของ B ไม่ได้, QR ผิดงาน/หมดอายุ/แก้ไขถูกปฏิเสธ, refresh ทุก 30 วินาทีไม่เปลี่ยน ticketId และไม่ล้างประวัติสแกน

### REQ-050: เข้า-ออกงาน

1. Kiosk หรือมือถือ Staff ที่มี `ticket.scan` ส่ง QR และ action `check_in` หรือ `check_out`
2. Server ตรวจผู้สแกน งาน ตั๋ว และสถานะเข้า-ออก
3. บันทึกผล เวลา และผู้สแกน พร้อมผลลัพธ์ที่หน้าจอใช้สื่อสารได้
4. สแกนซ้ำไม่สร้างรายการเข้า-ออกซ้ำ

DESIGN ที่รอ D09: ใช้สถานะ `outside/inside` แยกจากสถานะตั๋ว; `check_in` เมื่อ outside และ `check_out` เมื่อ inside; การกลับเข้าใหม่หลังออกต้องตกลงก่อนเปิดใช้ ไม่ใช้ `is_used` ตัวเดียวร่วมกับการซื้ออาหาร

Kiosk ต้องยืนยันตัวตนและสิทธิ์เช่นเดียวกับ Staff ไม่ใช่ endpoint สาธารณะ

ตรวจรับ: สองเครื่องเช็กอินตั๋วเดียวพร้อมกันสำเร็จเพียงครั้งเดียว; retry รายการเดิมคืนผลเดิม; scan ใหม่ขณะ inside ได้ `ALREADY_CHECKED_IN`; ทดสอบ checkout ขณะ outside และ re-entry ตาม D09

### REQ-060: กระเป๋าและ Token

1. Token แยกตามงาน มีเรทแปลงกับเงินบาทต่อ event
2. ได้รับตามบัตร เติมเพิ่ม ซื้อสินค้า ดูยอดและประวัติได้
3. มี ledger อธิบายที่มาของยอด ไม่เก็บเพียง balance ที่แก้ทับได้
4. ยอดห้ามติดลบ การตรวจและตัดยอดต้องเป็น atomic transaction
5. ผู้ใช้/ร้านแก้ balance โดยตรงไม่ได้

OPEN D02 กำหนดเจ้าของกระเป๋า; D05 กำหนดวิธีเติม ไม่ถือว่าการซื้อหลายบัตรทำให้ผู้ซื้อได้รับ Token ทุกใบในกระเป๋าตนโดยอัตโนมัติ

DESIGN: ทุกจำนวนใช้หน่วยจำนวนเต็มที่ตกลง บันทึกเรท snapshot, เครดิตจากบัตร/เติม/ตัดขาย/กันคืน/ปล่อยกัน/คืน/ย้อนรายการแยกประเภท การย้อนรายการทำรายการชดเชยอ้างถึงต้นฉบับ ห้ามแก้หรือลบ ledger เก่า

ตรวจรับ: คำขอซ้ำเครดิตครั้งเดียว, debit พร้อมกันไม่เกินยอด, event A ใช้ยอด event B ไม่ได้, ยอดรวม ledger ตรงกับ balance/ยอดที่ถูกกัน, แยก Token แถมกับ Token ที่เติมเพื่อรองรับ D07

### REQ-070: ร้าน สินค้า และการขาย

1. มีขั้นตอนสร้าง/สมัครร้านและอนุมัติ ตาม D04
2. ร้านมีเจ้าของและผู้ช่วยหลายบัญชีได้ ผ่าน `store_members` โดยต้องเป็นสมาชิก event เดียวกัน
3. แยกอนุมัติร้าน `pending/approved/rejected` กับเปิดขาย `closed/open`
4. ร้านที่ไม่ approved ห้ามเปิดขาย สินค้าต้องพร้อมขายและราคามาจาก server
5. Vendor สแกนรับชำระด้วย Token เห็นเฉพาะข้อมูลของร้านที่มีสิทธิ์
6. เมื่อยอดไม่พอ ต้องปฏิเสธทั้งรายการ ไม่สร้างยอดขายหรือ debit บางส่วน
7. สรุปยอด Token และมูลค่าเงินบาทตามเรทที่บันทึกตอนขาย

DESIGN: สร้าง store + owner + membership ที่ต้องใช้ใน transaction เดียว ห้ามร้านอนุมัติตนเอง ห้ามเอา owner คนสุดท้ายออก การถอนอนุมัติร้านที่เปิดอยู่ต้องปิดพร้อมกัน ห้ามเปลี่ยน `eventId` ของร้านหลังสร้าง

จำนวนสินค้าต่อร้าน/ต่อ sale ยังเป็น OPEN D03 ไม่ล็อกฐานข้อมูล one-product หรือ multi-product โดยไม่มีคำตอบ

ตรวจรับ: Vendor ร้าน A จัดการร้าน B ไม่ได้แม้อยู่ event เดียวกัน; approval จาก client ไม่มีผล; race ระหว่างปิดร้านกับขายต้องมีลำดับที่ตรวจสอบได้; debit, sale, sale items, stock และ audit สำเร็จ/ล้มเหลวร่วมกัน

### REQ-080: ขอคืน Token

1. ผู้ใช้ขอคืนยอดที่เข้าเงื่อนไขได้ในระยะ 7 วัน
2. ผู้มี `token.refund.approve` ตรวจ อนุมัติ หรือปฏิเสธได้
3. บันทึกผู้ขอ ผู้อนุมัติ เวลา จำนวน และผลการคืน
4. ห้ามอนุมัติ/ตัดยอด/คืนยอดซ้ำ

OPEN D07 ยังไม่ทราบวันเริ่มนับ 7 วันและ Token ที่คืนได้; D08 ยังไม่ทราบว่าจะกันยอดระหว่างรอหรือไม่; D10 ยังไม่ทราบว่าบันทึกการคืนเป็นจำลองหรือมีเงินจริง ห้ามตีความว่า approve เท่ากับโอนเงินธนาคารสำเร็จ

DESIGN ที่แนะนำ: กันยอดตอนขอ; `pending -> rejected` ปล่อยยอด หรือ `pending -> approved -> completed` ตัดส่วนที่กันและบันทึกผล; ถ้าขั้นตอนคืนล้มเหลวเก็บสถานะให้ retry โดยไม่คืนซ้ำ ต้องตัดสินใจกฎนี้ก่อน implement

ตรวจรับ: ใช้จ่ายส่วนที่กันไม่ได้ถ้าเลือก D08 แบบ hold; สอง admin อนุมัติพร้อมกันเกิดผลครั้งเดียว; rejected ไม่ตัด Token; boundary 7 วันใช้ timezone และเวลา server ที่ระบุ

### REQ-090: รายงาน Audit Export และอีเมล

- ค้นหารายชื่อ จำนวนลงทะเบียน/บัตร/เข้างาน ยอดขายร้าน และสรุป Dashboard โดยแยกคำนิยามตัวเลข
- กระทบยอด order/payment/ticket และ wallet/ledger/sale/refund ได้ ไม่รวมยอดซ้ำจาก JOIN หลายแถว
- Export เปิดใน Excel ได้ จำกัด event/store/คอลัมน์ตามสิทธิ์ พร้อม audit การ export
- เก็บประวัติการแก้ราคาเสื้อ/บัตร/Token/สินค้า/สิทธิ์ และการเปลี่ยนสถานะสำคัญย้อนหลังแก้ไม่ได้
- อีเมลในสไลด์เป็นแบบจำลองและมีสถานะการส่ง ต้องยืนยัน D13 ก่อนเชื่อมส่งจริง

## 5. สิ่งที่ไม่รวมโดยอัตโนมัติ

## 7. ขอบเขตความสัมพันธ์ที่ผู้ใช้ยืนยันแล้ว

`User -> UserEvent -> Event` และ `User -> StoreMember -> Store -> Event` รองรับหลายงาน/หลายร้าน ไม่ควรลดเหลือ `users.event_id` หรือ `users.store_id` ตัวเดียว

`user_events` เป็นสมาชิก/บริบทสิทธิ์ ไม่ใช่หลักฐานซื้อบัตร ไม่ใช่ attendee และไม่ใช่ admission การเข้าร่วมเป็นสมาชิกงานเฉย ๆ ต้องไม่ออกตั๋วหรือเครดิต Token
